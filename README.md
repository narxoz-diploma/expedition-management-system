# Step Up

Сайт студенческого горного клуба Step Up при Narxoz University.

Сайт живёт на https://step-up-gold.vercel.app.

Этот файл — для того, кто получит проект после автора. Всё остальное — в
`docs/`: [PROJECT](docs/PROJECT.md) (зачем), [PRD](docs/PRD.md) (правила),
[SCREENS](docs/SCREENS.md) (экраны), [DESIGN](docs/DESIGN.md) (бренд),
[ROADMAP](docs/ROADMAP.md) (порядок работ). База — в `supabase/migrations/`.

Ещё два, которые открывают не «зачем», а «как»: [UI](docs/UI.md) — ширины,
отступы, анатомия карточек; открывать **до** вёрстки любого экрана, а не после.
[PERF](docs/PERF.md) — разбор задержки: что мерили, что нашли, чем чинили;
открывать прежде, чем оптимизировать что-либо по ощущениям.

## Что уже работает

MVP собран целиком: вход без паролей, походы, запись с листом ожидания,
членство, снаряжение, экран группы для лидера, лендинг. Сверх MVP: прогноз
погоды на точке маршрута и фотографии — альбомы походов, обложки в карточках,
галерея и герой лендинга, аватары.

Из работы 19 августа 2026: сборка чата похода в WhatsApp по одному человеку,
справочник клуба с поиском и отметками общего чата, удаление своих данных со
сроком хранения, физическая форма в профиле. Ворот по категориям сознательно
нет — почему, в [PRD §3](docs/PRD.md).

| | |
|---|---|
| **Публичное** | `/` (лендинг гостю, лента своему), `/hikes`, `/hikes/[slug]`, `/rules`, `/gear-guide` |
| **Личное** | `/login`, `/profile`, `/profile/edit`, `/profile/gear`, `/profile/join` |

**Чего ещё не было: ни один настоящий поход через сайт не прошёл.** Это
обязательное условие запуска из роадмапа, и оно важнее любой доработки.
Тестовый поход убран в черновики — значит для прогона сперва нужно
опубликовать будущий поход, иначе половину списка ниже проверять не на чем.

Навигация в августе 2026 переделана, разбор и причины — в
[DESIGN §5a](docs/DESIGN.md); интерфейс сведён к правилам из
[UI](docs/UI.md). Из того списка остался один невыполненный пункт — ритм
отступов, он последний в конце `UI.md`.

Текущее состояние всегда в [ROADMAP](docs/ROADMAP.md), раздел «Где мы сейчас».

## Запуск локально

Нужен Node.js 24 (та же мажорная версия, что на Vercel).

```bash
npm install
```

Дальше скопировать `.env.example` в `.env.local` и подставить значения из
панели Supabase (Project Settings → API). **Без них не поднимется ничего,
включая главную:** обновление сессии живёт в `src/proxy.ts` и срабатывает на
каждый запрос.

```bash
npm run dev
```

Откроется на http://localhost:3000.

| Команда | Что делает |
|---|---|
| `npm run dev` | дев-сервер |
| `npm run build` | продакшн-сборка, та же, что на Vercel |
| `npm run lint` | ESLint |
| `npm run typecheck` | проверка типов без сборки |
| `npm test` | всё сразу; тест конкурентности пропускается, если нет Docker |
| `npm run test:unit` | тесты кода |
| `npm run test:schema` | миграции и тесты базы, ~3 секунды |
| `npm run test:concurrency` | гонка за места, нужен Postgres в Docker |

**Перед коммитом прогонять четыре: `typecheck`, `lint`, `test`, `build`.** Все
должны вернуть 0 — проверять именно код возврата, а не глазами: `| tail` в
конвейере прячет падение, на этом уже обжигались.

И ещё одно, чего четыре команды не ловят: **экспортированный, но нигде не
использованный компонент линтер не видит.** Всё зелёное, а на экране пусто.
Написав экран, открыть его и посмотреть — на 390px в том числе.

## База данных

Supabase (Postgres + Auth + RLS). Схема лежит в `supabase/migrations/` и
применяется файлами по порядку имён.

**Менять схему только новой миграцией, а не правкой старой:** старые уже
применены к рабочей базе, и правка в файле туда не доедет.

**Миграции применяются вручную**, копипастой в SQL-редактор Supabase — CLI к
проекту не подключён. Значит порядок такой: написал миграцию → применил её →
только потом выкатил код, который на неё рассчитывает. Иначе прод сломается на
время между push и применением.

Применено на сегодня:

Если CLI однажды подключат, первую миграцию придётся пометить применённой:
`npx supabase migration repair --status applied 20260803120000` (и так далее
по списку), иначе `db push` попробует накатить всё заново.

`npm run test:schema` поднимает настоящий Postgres, собранный в WebAssembly
(PGlite), накатывает на него все миграции с нуля и проверяет поведение —
запись в поход, лист ожидания, отмену, права. Ни Docker, ни подключение к
рабочей базе не нужны, весь прогон занимает около трёх секунд. Этот тест уже
один раз оправдался: он поймал, что `register_for_hike()` вообще не работала
из-за конфликта имени выходного параметра с колонкой.

Конкурентность этот тест проверить не может: PGlite однопоточный, и блокировке
в `register_for_hike()` там не с кем конкурировать. Для неё есть отдельный
тест на настоящем Postgres в Docker:

```bash
docker run -d --name stepup-pgtest -e POSTGRES_PASSWORD=test -e POSTGRES_DB=stepup -p 55432:5432 postgres:16
```

```bash
npm run test:concurrency
```

Он бьёт по походу на 5 мест двадцатью **параллельными соединениями** — по
одному на участника, иначе запросы выстроились бы в очередь и тест проходил бы
даже без всякой блокировки. Проверяется, что подтверждено ровно 5, позиции в
очереди идут 1..15 без дыр и дублей, счётчик мест сошёлся, и что одновременная
отмена пяти мест поднимает из очереди ровно пятерых.

Тест проверен на способность падать: с наивной реализацией (посчитать и
вставить, без `FOR UPDATE`) он показывает 10 подтверждённых на 5 мест. Если
однажды кто-то «упростит» `register_for_hike()`, этот тест это поймает.

Если Postgres на `localhost:55432` недоступен, тест не падает, а помечается
пропущенным с объяснением причины — поэтому он включён в общий `npm test` и не
ломает его на машине без Docker. Проверяется именно доступность базы, а не
наличие контейнера: остановленный контейнер существует, но подключиться к нему
нельзя.

Второе слепое пятно PGlite, кроме конкурентности: **`session_user` там всегда
`postgres`, и понизить его нельзя** — `set session authorization` не
отыгрывается обратно даже откатом транзакции, так что дальнейшие тесты пошли бы
от чужого имени. Поэтому проверки вида «служебная роль проходит, обычный
пользователь нет» этим стендом не берутся. Там, где это важно, защита строится
не на такой проверке, а на отобранных правах — их-то тест видит: см.
`ban_member` и `unban_member`.

Четыре вещи, которые нельзя обходить:

1. **Запись в поход — только через `register_for_hike()`.** Прямой `INSERT` в
   `registrations` закрыт политиками намеренно: это единственная защита от
   перебора мест, когда сто человек жмут кнопку одновременно.
2. **RLS включён на всех таблицах.** Анонимный ключ Supabase лежит в клиентском
   бандле, база доступна из интернета.
3. **Экстренные контакты** видит только владелец и лидер того похода, на который
   человек записан.
4. **Триггеры-сторожа на `profiles` и `hikes` не снимать.**
   `profiles_guard_privileges` не даёт человеку выдать себе роль, поменять
   статус членства, обнулить счётчик неявок или снять с себя запрет на запись.
   `hikes_guard_responsible` не даёт сменить `leader_id`: править поход вправе
   любой лидер из состава, и без этого триггера второй лидер переписывал бы
   ответственного на себя прямым запросом — вместе с доступом к экстренным
   контактам всей группы. Политикой это не выражается, `WITH CHECK` не видит
   `OLD`. Оба закрыты тестами в `supabase/tests/`, и оба теста проверены на
   способность падать.

Первый администратор назначается вручную, SQL в конце файла схемы.

### Что делается руками из SQL-редактора

Экрана для этого нет намеренно — случаи исключительные, и решаться они должны
разговором, а не кнопкой под рукой. Но узнать о них иначе, чем прочитав
миграции, нельзя, поэтому список здесь.

**Закрыть человеку запись на походы** и снять его с будущих. Возвращает число
снятых записей; освободившиеся места уходят очереди. Причина хранится для
клуба, на экране человек видит нейтральное «запись сейчас закрыта, напиши
лидеру» — без клейма, потому что страницу открывают и с чужого телефона.

```sql
select ban_member('<uuid>', 'причина, коротко');
```

```sql
select unban_member('<uuid>');
```

Права на вызов у клиента отозваны: PostgREST публикует как RPC всё из схемы
`public`, а раз выдача только из базы — двери быть не должно. Появится экран в
админке, права вернутся вместе с ним.

**Вернуть отменённый поход.** Через интерфейс нельзя: у отменённого нет кнопки
публикации, и в подтверждении об этом сказано прямо. Если всё же нужно:

```sql
update hikes set status = 'published', cancelled_reason = null where slug = '<slug>';
```

Записи участников при отмене не трогаются — по ним лидер и понимает, кого
обзванивать, — так что после возврата группа на месте.

## Вход

Паролей нет и не будет — только Google OAuth и ссылка на почту (magic link).

Что настроено вне репозитория и что сломается, если это потерять:

- **Google Cloud** — OAuth client. В список Authorized redirect URIs должен быть
  внесён `https://<проект>.supabase.co/auth/v1/callback` — адрес Supabase, а не
  адрес сайта.
- **Supabase → Authentication → Providers → Google** — туда кладутся client ID
  и secret из Google Cloud.
- **Supabase → Authentication → URL Configuration** — Site URL и список
  Redirect URLs. Адрес каждого превью-деплоя Vercel свой, поэтому нужен шаблон
  вида `https://step-up-*.vercel.app/**`, иначе вход будет работать только на
  проде.

`src/lib/in-app-browser.ts` определяет, что страница открыта во встроенном окне
мессенджера: Google в таком окне отвечает `disallowed_useragent` и вход через
него не работает вовсе. Тогда показывается баннер «открой в браузере», а вход
по ссылке на почту доступен всегда — на случай, если определение промахнётся.

### Письма

Проект не отправляет писем сам: во всём коде одна точка,
`supabase.auth.signInWithOtp()` в `src/app/[lang]/login/login-form.tsx`. Всё остальное
делает Supabase Auth. Поэтому смена почтового провайдера — настройка в панели
Supabase, кода она не касается вообще.

**Resend отложен: своего домена у клуба нет.** Подключать его с чужого адреса
бессмысленно — половина пользы Resend в том, что письма идут с подтверждённого
домена и не считаются спамом. Пока домена нет, действует встроенный SMTP
Supabase со всеми его ограничениями, а magic link на экране входа свёрнут под
строчку «Не получается?»: чем меньше людей идёт через почту, тем позже упрётся
почасовой лимит. Всё, что ниже, — инструкция на день, когда домен появится.

**Встроенный SMTP Supabase годится только для проверки вдвоём.** На бесплатном
тарифе он отдаёт единицы писем в час, и упирается в это не тот, кто настраивал,
а тридцатый первокурсник в вечер набора. Симптом самый неудобный из возможных:
не ошибка, а тишина — человек видит «письмо отправлено» и ждёт ссылку, которой
не будет. К утру лимит отпускает, поэтому при проверке малым числом людей
проблема не воспроизводится никогда.

Что для этого настраивается вне репозитория:

- **Resend** — аккаунт и подтверждённый домен клуба (DNS-записи SPF и DKIM).
  Домен нужен не ради галочки: письма с чужого домена заметно чаще уходят в
  спам, а спам здесь равен «не смог войти».
- **Supabase → Project Settings → Authentication → SMTP Settings** — хост,
  порт, логин и пароль Resend, плюс адрес отправителя на подтверждённом домене.
- **Supabase → Authentication → Rate Limits, лимит на письма в час.** Отдельный
  потолок, который живёт своей жизнью и остаётся на месте после подстановки
  чужого SMTP. Если его не поднять, всё упрётся в него же и с тем же симптомом,
  просто на другом числе — а выглядеть будет как «Resend не работает».

Потолки самого Resend на бесплатном тарифе — порядка 3000 писем в месяц и около
сотни в сутки. Месячного запаса хватает с огромным зазором, суточный реален:
набор в сотню человек за один вечер в него упрётся, за два-три вечера нет.
Цифры сверять на сайте Resend, тарифы меняются.

Ошибку с превышением лимита форма входа уже переводит в «Слишком много запросов
подряд, подожди минуту» — сырой текст пользователю не показывается.

## Деплой

Автоматический: push в `main` → Vercel собирает и выкатывает на прод. У каждой
ветки свой превью-адрес.

**Порядок с миграциями обратный привычному:** сначала применить SQL руками,
потом пушить код. Между push и применением прод работает на старой схеме, и
код, который рассчитывает на новую, всё это время падает.

**Результат проверять запросом к проду, а не на веру.** Сборка может пройти, а
страница отдавать пустоту — например, если сломался запрос к Supabase.

**`vercel.json` держит регион `sin1` (Сингапур) — не удалять.** База стоит в
Сингапуре, а по умолчанию функции считались бы в Вашингтоне: каждый запрос
пересекал Тихий океан дважды, страницы открывались в два-пять раз медленнее.
Одна строчка в этом файле — самая дешёвая оптимизация в проекте, и потерять её
при пересоздании проекта на Vercel легче всего. Замеры и метод — в
[PERF](docs/PERF.md).

## Что проверить перед запуском на людях

Прогон удобно разбить надвое: половина проверяется откуда угодно, половина
только в горах.

**Нужен опубликованный будущий поход.** Половина списка ниже живёт на его
странице — место сбора, расписка, блок записи, — и на пустой вкладке
«Ближайшие» проверять нечего. Заводится он за минуту на `/admin/hikes/new`;
после прогона убирается в черновики.

**Без гор, хоть сегодня — 5–8 человек и один вечер:**

- **Вход через Google из встроенного браузера.** В WebView он не работает:
  окно получает `disallowed_useragent`. **По WhatsApp риск снят частично** —
  9 августа 2026 ссылку открыли несколько лидеров с разных телефонов, у всех
  она ушла в настоящий браузер и вход прошёл; переключателя встроенного
  браузера в их сборках WhatsApp нет. Остался **Instagram**: там окно не
  отключается, а ссылка на клуб стоит на лендинге и в подвале — этот путь не
  проверял никто. Проверять на реальных телефонах, не в эмуляторе.
- **Мини-профиль:** шесть полей и экстренный контакт, с телефонами в том виде,
  в каком их пишут люди.
- **Запись, лист ожидания, отмену.** Поставить вместимость 2–3, чтобы очередь
  действительно двигалась. Нажать «Записаться» одновременно — заодно проверка
  конкурентности на настоящей базе, а не только в тесте.
- **Место сбора.** Незаписанный видит время выхода и подпись «адрес — тем,
  кто записан»; записавшийся — сам адрес и ссылку на карту. Это единственное
  поле похода, закрытое поколоночно, и ошибка тут видна только глазами.
- **Расписку.** Плашку на карточке, скачивание обоих бланков, имя файла в
  «Загрузках» на телефоне — и что человеку показывается бланк по его
  возрасту, а не оба сразу.
- **Галочку «родитель».** Несовершеннолетнему профиль без неё сохраняться не
  должен; в составе группы и в XLSX рядом с контактом обязано появиться
  «(родитель)».
- **Поле «где уже был»** — в профиле и строкой в составе группы у лидера.
- **Сборку чата** (`Собрать чат` на экране группы). Копируется ли номер
  нажатием, открывает ли «Написать» личный чат в WhatsApp с тем, кого нет в
  контактах, держится ли отметка после возвращения из другого приложения.
  Проверять на телефоне: во встроенном окне мессенджера доступ к буферу
  обмена ведёт себя иначе, чем в браузере.
- **Выгрузку XLSX**, открытую на телефоне лидера, а не на ноутбуке.
- **Анонс:** скопировать, отправить в чат, посмотреть, как встало превью
  ссылки.
- **Мобильный вид на 390px** на каждом экране.

**Только на маршруте:**

- **окно отметок явки** — до выхода кнопки серые и стоит строка «отметить
  можно с …», после открытия повторное нажатие снимает отметку. Окно
  открывается за два часа до выхода, так что без гор это проверяется только
  походом, назначенным на ближайший час;
- отметку явки без связи;
- снаряжение в реальности против отметок в профиле;
- отмену по погоде;
- поведение группы на 20–25 человек.

**Отдельно, до набора:** отправку писем через Resend. Встроенный SMTP Supabase
на бесплатном тарифе ограничен единицами писем в час и ляжет на первой же
волне регистраций.
